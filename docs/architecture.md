# 0xbot 架构基线

状态：首版实现中。四个项目已创建，真实查询与认证闭环已完成验证。

## 定位

一个标准接口，接入多个 Web3 服务提供商。持续积累能力协议与 Provider Adapter；MCP 是 AI 接入方式之一。

## 交付单元

| 目录 | 域名 | 职责 |
| --- | --- | --- |
| website | 0xbot.org | 中英文官网与文档 |
| app | app.0xbot.org | 用户控制台与 Playground |
| dashboard | dashboard.0xbot.org | 内部管理 |
| api | api.0xbot.org | API、路由、适配器、MCP、任务 |

四个项目独立仓库和部署，不以相对路径共享业务源码。

## 依赖方向

前端 → 版本化 REST 契约 → 应用用例 → 领域规则与端口。

MCP → 同一应用用例。

Provider、数据库、缓存适配器实现端口，由启动入口装配。只有边界层理解外部格式。能力模块不负责供应商 SDK 细节，Provider Adapter 不决定平台业务政策。

## 技术选型

后端语言已确定为 Go，前端使用 TypeScript。官网 Next.js / MDX；应用与管理端 React / Vite。

API 采用 Go 1.26.8 模块化单体，使用 net/http + chi、PostgreSQL + pgx、标准库 slog 日志和官方 MCP Go SDK。首版使用显式参数化 SQL 与嵌入式事务迁移，sqlc/goose 暂缓引入，理由见 [ADR 0002](adr/0002-preview-runtime.md)。按需引入 Redis 与独立 worker；使用 Docker Compose 部署。REST 与 MCP 复用 Go 应用用例，通过 OpenAPI 生成前端 TypeScript 客户端。

Provider 优先通过 HTTP API 接入；必须使用 JS SDK 的能力经独立适配服务承接，不使 Go 业务核心依赖 JS 运行时。具体依赖、兼容性及版本在实施时核对锁定。语言决定见 [ADR 0001](adr/0001-go-backend.md)。

## 身份与账号

- 用户统一通过 Web3 钱包签名或 X 授权登录；首次成功认证自动注册，后续进入已有账号。首版没有邮箱密码注册入口。
- 钱包首批以 EVM 身份为范围；其他链身份通过独立适配器扩展。连接钱包不等于认证，需完成服务端可验证的一次性登录挑战。
- X 用户可直接进入控制台并使用 API Key、查询等能力；需要链上授权的操作再连接钱包。X 登录本身不生成或托管钱包。
- 内部 user_id 是账号主键；wallet 和 X 等外部身份独立关联到账号。X 采用稳定用户 ID，钱包标识明确网络命名空间并规范化。
- 已登录用户可主动绑定另一种身份，绑定时验证双方控制权。身份已属于另一个账号时提示冲突；不根据同名、邮箱或其他推测自动合并。
- 解绑需重新验证且保留至少一种可用登录方式。注销、会话撤销及账号恢复边界在实施设计中明确。
- 登录签名只用于身份验证，不授权交易、付款或自动发送消息。Agent 能力授权另行管理。
- dashboard 不开放公众自助注册为管理员；相同身份入口若复用，仍须显式授予管理员角色并满足独立会话及多因素认证策略。
- 官网和 app 的认证文案中英文一致，处理拒签、取消授权、挑战过期和绑定冲突。实施前核对钱包签名标准与 X 当前官方授权要求，接入真实 X 应用凭证及回调配置。

## 设计令牌

背景 #F7F3EA，面板 #FFFCF6，主文字 #302A23，次文字 #756B60，强调 #A64B35，边框 #DED5C7。实现时检查实际搭配对比度，允许必要调整。统一字体、间距、圆角、焦点与状态规则；官网留白较多，控制台信息密度更高。

三个前端均支持中英文。地址、技术 ID 不翻译；日期、数量按语言环境呈现。

## 交付阶段

1. 明确首个能力、两个具有重叠覆盖的 Provider、接口契约与页面流程。
2. 初始化四个项目，完成国际化、认证、工作区与本地运行。
3. 接入两家真实 Provider，实现标准查询、路由、记录、Playground 与计量。
4. 检查服务器，配置域名、HTTPS、健康检查、备份和版本化部署。
5. 按需求扩展消息、兑换、支付；逐项验证授权与执行状态。

首版验收：同一 Key 和标准接口切换两个真实 Provider，用户能查看调用记录，管理员能管理路由。模拟数据不得替代真实验收。
